# ADR-007: 計測とエラー監視を「口」だけにする

## ステータス

採用（2026-09-13）／決定者: 担当 B9（Analytics・エラー監視）

---

## 背景

CLAUDE.md §31 は 9 件のイベント（`app_started` ほか）を、task.md §18 は Analytics とエラー監視の導入を求めている。一方 §19 は依存を足す前にプラットフォームで足りないかを確かめることを、§30 は集める個人情報を最小限にすることを求めている。

## 決定

1. **事業者の SDK（PostHog / Sentry / GA 等）を入れない。** 送信先 URL を環境変数から受け取り、JSON を 1 回 POST するだけの口を置く（`src/features/telemetry/sink.ts`）。
2. **利用者が書いた内容は送らない。** これを規律ではなく型で担保する。イベントのペイロードは `TelemetryEventMap` が定めた数値・真偽値・固定リテラルだけで、素の `string` を受け付けない。ノード本文・マップのタイトル・メールアドレスはいずれも自由な文字列なので `track()` に渡せない。
3. **エラーはメッセージ本文を送らない。** 送るのは種類名（`TypeError` 等）・発生箇所ラベル・スタックのフレーム行のみ。
4. 送信先が未設定なら**本番では何もしない**。開発時だけ `console.debug` に出す。
5. 送信は**失敗してもアプリに影響させない**（例外を投げない・`await` させない）。

## 理由

- SDK はどれもアカウント登録と API キーが要り、どこへ何を送るかは事業者選定そのもの。実装の都合で決めてよい話ではない。差し替え先は 1 ファイルなので、先に入れておく利益が無い。
- メッセージ本文を落とすのは、そこが**唯一の構造的な漏洩経路**だから。`new Error("保存に失敗: " + node.text)` のような文字列連結は自然に書かれてしまう。フィルタで削ろうとすると「消し漏れたら漏れる」形になるが、フィールドごと持たなければ漏れようがない。種類名とフレーム行があれば、どのコードのどの行かは特定できる。
- 送信の失敗を握りつぶすのは §29 と同じ考え方。同期が落ちても編集は続くのだから、計測が落ちて編集が止まるのは論外。

## 事業者を選ぶときの判断基準

1. **送信先を URL 1 本で差し替えられるか**（SDK 必須でないか。多くは HTTP ingest を持つ）。
2. Cloudflare Workers / OpenNext のランタイムで動くか（ADR-001）。
3. 無料枠で Phase 1 の規模を賄えるか（§40-5）。
4. 収集するものを**こちらが決められるか**。自動収集（全クリック・入力値・セッション録画）を切れない製品は、ノード本文が入るので使わない。
5. バンドルへの影響（§19）。エディタの初期表示を遅らせないこと。

決めたらこの ADR を更新し、`sink.ts` の `post()` を差し替える。呼び出し側（`track` / `reportError`）は触らない。

## 影響

- 環境変数は `NEXT_PUBLIC_ANALYTICS_ENDPOINT`（イベント）と `NEXT_PUBLIC_ERROR_ENDPOINT`（エラー）の 2 本。分けてあるのは、計測とエラー監視は別事業者になるのが普通で、片方だけ有効にしたいことがあるため。どちらも `NEXT_PUBLIC_` なのでクライアントに露出する。**秘密情報を入れないこと。**
- `map_edited` は `trackMapEdited()` の側で 1 分に 1 件へ間引く。§31 の「打鍵ごとに出さない」を呼び出し側の規律に委ねない。
- イベントを増やすときは §31 を先に更新する。型に足しただけの追加はしない。

## 再評価の条件

- 事業者を選定したとき。
- エラーの種類名とフレーム行だけでは原因を追えない事例が実際に出たとき（そのときも本文全体ではなく、安全と分かっている文言の許可リストを検討する）。
