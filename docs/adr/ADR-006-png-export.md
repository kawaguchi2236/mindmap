# ADR-006: PNG 書き出しで折りたたみノードをどう扱うか

## ステータス

採用（2026-09-13）／決定者: 担当 B6（PNG エクスポート）。担当 A も同意。

---

## 背景

CLAUDE.md §16 は PNG に「マップ全体・ノード・接続線・現在の配色・背景」を含めることを求めている。一方で Phase 1 には折りたたみ（collapse）があり、**折りたたまれた子孫を書き出しに含めるか**はどこにも書かれていない（要件定義にも task.md にもない）。実装するには決めるしかない。

## 決定

1. **「見たまま」を出す。折りたたまれて画面に出ていない子孫は PNG にも出さない。**
2. 実装上は React Flow の `getNodes()`（表示中のノードだけを返す）から外接矩形を取り、それを `exportMapToPng` に渡すことでこの挙動になる。折りたたみを判定する専用のコードは書かない。
3. §16 の「マップ全体」は**ズーム・スクロール位置に依存しないこと**を指すものとして実装する。出力の大きさと transform はノードの外接矩形からのみ計算し、現在のビューポートは一切参照しない。

## 理由

- ユーザーが意図的に畳んだ枝が勝手に展開されて出てくるほうが、驚きが大きい。折りたたみは「今はこの粒度で見たい」という明示的な操作なので、書き出しもその粒度に従うのが素直。
- 折りたたんだ状態は「要約された図」を作る手段として実際に使われる。展開して出すとその用途が消える。
- 全展開で出すと、畳んだ枝の分だけ画像が予告なく巨大になる。上限に当たって全体が縮小され、見たかった部分が読めなくなる。
- 実装が単純になる（レイアウトの再計算も、非表示ノードの採寸もいらない）。畳んだ枝を含めるには「表示していないノードを一度描画して測る」必要があり、Phase 1 に見合わない複雑さになる。

## 却下した案

- **常に全ノードを展開して書き出す。** 「全体」の語をノード集合の全体と読む解釈。上記の理由で却下。
- **書き出し時に「折りたたみを含めるか」を尋ねる。** 質問のためのモーダルが編集の流れを止める（CLAUDE.md §40-2）。選択肢が必要になるまで作らない。
- **書き出し前に自動で全展開し、終わったら畳み直す。** 画面がちらつき、Undo 履歴にも影響しかねない。データに触れる処理を書き出しのために走らせるのは §6 の方針に反する。

## 再評価の条件

次のどれかが起きたら見直す。

- ユーザーから「畳んだ枝も含めて書き出したい」という要望が実際に出たとき。
- PDF/SVG など複数形式の書き出しを足すとき（書き出しオプションの UI を作る機会になるため、そこで選択式にできる）。
- 印刷・共有用途で「全体像を 1 枚で」というニーズが要件に入ったとき。

見直す場合も既定は「見たまま」のままにし、全展開は明示的なオプションとして足す。

## 付随する決定（記録のみ）

- 出力サイズの上限は 1 辺 8192px / 総計 16,000,000px。超えるときは**縦横比を保ったまま全体を縮小**し、縮小率をボタン横に表示する（切り詰めない・黙らない）。
- 背景は透明にせず、`.react-flow__viewport` の祖先の実描画色を拾ってテーマに追従させる。拾えないときは `data-theme` と OS 設定から保険の色を決める。
- 書き出しの失敗は例外にせず結果オブジェクトで返す。エディタの編集は止めず、同じボタンで再試行できる（CLAUDE.md §29）。
