# ADR-005 同期競合の判断表

- ステータス: 採用（Phase 1）
- 対象: `src/features/sync/decide.ts`（判定）/ `src/features/sync/engine.ts`（実行）
- 関連: CLAUDE.md §6 データ安全、§12 オフライン、§13 同期競合戦略、§32 ADR-005

---

## 1. 決定

Phase 1 では CRDT も OT も使わない。**マップ単位の楽観ロック**（`version` による）だけで判定し、
判断がつかない組み合わせは **ローカル版を複製して両方残す** ことで解決する。

判定は副作用のない純関数 `decideSyncAction(local, remote)` に閉じ込め、
実行（HTTP・ローカル保存）は `engine.ts` が行う。判断表とテストが 1 対 1 に対応する。

## 2. 前提と用語

| 用語              | 定義                                                                                      |
| ----------------- | ----------------------------------------------------------------------------------------- |
| `map.version`     | マップ内容の単調増加版数。ローカル編集のたびに +1、サーバは PUT 成功時に確定値を返す      |
| `syncedVersion`   | 最後にサーバと一致した `version`。未同期は `0`。**次回 PUT の `baseVersion`** になる      |
| `dirty`           | ローカルに未送信の変更がある印。保存時に立てる                                            |
| `localHasUnsent`  | `dirty \|\| map.version > syncedVersion` — **どちらか一方でも立てば未送信扱い**（安全側） |
| `remoteHasUnseen` | `remote.version > syncedVersion`                                                          |
| 削除              | `deletedAt !== null` の論理削除。物理削除は同期完了後にのみ行う                           |

**重要な前提**: 突き合わせに使うサーバ一覧は `GET /api/maps`（`since` なしの全件）である。
論理削除分も含まれるため、「一覧に出ない ＝ サーバに存在しない」と解釈してよい。
`since` 付きの差分取得を突き合わせに使うと、更新のないマップが「サーバから消えた」と誤判定される。

**`?since=` の取りこぼしレースへの対応**: `syncAll` は常に全件突き合わせを行い、`since` を使わない。
サーバの `updated_at` は COMMIT 時刻ではなく `now()` 評価時刻なので、前回の最大 `updatedAt` を
そのまま次の `since` にすると同時刻の別トランザクションを取りこぼす。マージンを引く方式ではなく、
「毎回 `since` なしで全件」を採った。Phase 1 のマップ数（1 ユーザーあたり数十件）では全件取得が
十分に安く、取りこぼしの可能性を構造的にゼロにできるため。`RemoteClient.listSummaries(since)` は
将来の差分取得のために口だけ残してあるが、使う場合は数十秒のマージンを引くこと。

**サーバ側の楽観ロック仕様**（担当 B2 実装、`src/app/api/maps/[id]/route.ts`）:

- `version` はサーバが決める。`baseVersion` が一致したときだけ `version + 1`。
  クライアントが送った `map.version` は読まれない。
- 行が無い場合、`baseVersion === 0` のときだけ新規作成（`version = 1`）。
  `baseVersion > 0` で行が無ければ **404**（物理削除済み、または別ユーザーのマップ）。
- `updated_at` は常にサーバ時刻で上書き。`created_at` はクライアント値を採用。

## 3. 判断表

`reason` 列の値は `SyncAction.reason` の文字列リテラルであり、`tests/sync/decide.test.ts` の
テスト名とも一致する。表を直せばコードとテストの両方が直る、という対応を維持すること。

### 3.1 片側にしか存在しない

| #   | reason                | 判定条件                                   | 動作                       | 理由                                                                                                                            |
| --- | --------------------- | ------------------------------------------ | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `both-absent`         | local, remote ともになし                   | `noop`                     | 対象がない（防御的分岐）                                                                                                        |
| 2   | `local-only-new`      | remote なし / `syncedVersion === 0` / 生存 | `push`（`baseVersion: 0`） | 未アップロードの新規マップ。ゲストマップもここに落ちる                                                                          |
| 3   | `local-only-deleted`  | remote なし / ローカルは削除済み           | `noop`                     | サーバに無いものを消す必要はない。ローカルの墓標だけ残す                                                                        |
| 4   | `local-only-vanished` | remote なし / `syncedVersion > 0` / 生存   | `push`（`baseVersion: 0`） | 一度同期したのにサーバから消えた（物理削除・DB 障害）。**復活させる。**「余計な 1 件」より「消えた 1 件」の方が害が大きい（§6） |
| 5   | `remote-only-alive`   | local なし / `deletedAt === null`          | `pull`                     | 他デバイスで作られたマップ                                                                                                      |
| 6   | `remote-only-deleted` | local なし / サーバで削除済み              | `noop`                     | 墓標をわざわざ取りに行かない                                                                                                    |

### 3.2 両側にあり、どちらも生存

| #   | reason          | 判定条件                              | 動作                                   | 理由                                                                                                                                                   |
| --- | --------------- | ------------------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 7   | `in-sync`       | `!localHasUnsent && !remoteHasUnseen` | `noop`                                 | 一致している                                                                                                                                           |
| 8   | `local-newer`   | `localHasUnsent && !remoteHasUnseen`  | `push`（`baseVersion: syncedVersion`） | ローカルだけが進んでいる。`baseVersion` が一致しなければサーバが 409 を返すので、競り合いは検出できる                                                  |
| 9   | `remote-newer`  | `!localHasUnsent && remoteHasUnseen`  | `pull`                                 | サーバだけが進んでいる。捨てるローカル変更はない                                                                                                       |
| 10  | `both-modified` | `localHasUnsent && remoteHasUnseen`   | `forkLocalCopy`                        | **両方が変更された。どちらが正しいか機械には判断できない。** ローカル版を新 ID で複製して残し、元の ID にはサーバ版を入れる。ユーザーに通知する（§13） |

> `version` が同値なのに `updatedAt` がずれている場合（時計ずれ・版数の進め忘れ）は、
> `dirty` が立っていれば #8 か #10 に落ちる。`dirty` を `localHasUnsent` の OR 条件に
> 入れているのは、この「版数を信用できない」ケースを安全側に倒すためである。

### 3.3 削除がからむ

| #   | reason                          | 判定条件                                           | 動作                                         | 理由                                                                                                                                               |
| --- | ------------------------------- | -------------------------------------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 11  | `local-deleted`                 | ローカル削除済み / サーバ生存 / `!remoteHasUnseen` | `pushDelete`（`baseVersion: syncedVersion`） | ユーザーの削除意思をサーバに伝える。サーバ側に未取得の変更はない                                                                                   |
| 12  | `local-deleted-remote-modified` | ローカル削除済み / サーバ生存 / `remoteHasUnseen`  | `pullRestore`                                | 「こちらで削除」対「あちらで編集」。**編集の方を残す。** 削除は 1 クリックでやり直せるが、失われた編集は戻らない。復元したことをユーザーに知らせる |
| 13  | `remote-deleted`                | サーバ削除済み / ローカル生存 / `!localHasUnsent`  | `applyRemoteDelete`                          | 他デバイスの削除を受け入れる。ローカルでも論理削除にとどめ、ノードは保持する                                                                       |
| 14  | `remote-deleted-local-modified` | サーバ削除済み / ローカル生存 / `localHasUnsent`   | `forkLocalCopy`                              | 「あちらで削除」対「こちらで編集」。未送信の編集を消さないため、ローカル版を新 ID で複製してから削除を適用する                                     |
| 15  | `both-deleted`                  | 両方とも削除済み                                   | `noop`                                       | 合意済み。物理削除は別途のクリーンアップに任せる                                                                                                   |

### 3.4 初回ログイン時のゲストマップ

| #   | reason              | 判定条件                        | 動作                       | 理由                                                                    |
| --- | ------------------- | ------------------------------- | -------------------------- | ----------------------------------------------------------------------- |
| 16  | `guest-first-login` | `record.userId === null` / 生存 | `push`（`baseVersion: 0`） | 判定自体は #2 と同じ。`migrateGuestMaps()` が明示的に列挙して push する |

ゲスト移行の不可侵ルール:

- **push が成功してもローカルのレコードを削除しない。** `userId` を書き込むだけにする。
- push が失敗したマップはゲストのまま `dirty` で残す。次回の同期で再試行される。
- サーバに同じ ID が既にある場合（別デバイスで移行済み等）は 409 が返る。→ `forkLocalCopy` に倒す。
- 所有者の付け替えは `putLocal` に `userId` を載せた上書きで表現する。担当 A の
  `claimGuestMaps(userId)` と同じ「付け替え」であり、**delete + create では実装しない**。
  同期エンジンは `deleteLocalHard` をどの経路でも呼ばない（テストで保証している）。

### 3.5 実行時にしか分からない競合

判定（`decideSyncAction`）ではなく `engine.ts` が実行中に検出する行。

| #   | reason                    | 判定条件                                                      | 動作                                                                | 理由                                                                                                                                                                                                     |
| --- | ------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 17  | `push-404-revive`         | `push` に対しサーバが 404（`baseVersion > 0` で行が無い）     | `baseVersion: 0` で 1 度だけ再 push                                 | サーバ側で物理削除された、または同期メタがずれた。#4 と同じく復活を選ぶ。再試行は 1 回だけで、2 度目の 404 は失敗として記録しループしない                                                                |
| 18  | `local-store-stale-write` | サーバ版の書き戻しを `LocalStore` が `StaleWriteError` で拒否 | **ローカル優先。** 元 ID は触らず、サーバ版を新 ID の複製として保持 | ローカルの方が新しいと担当 A の `saveMap` が拒否する。拒否は異常ではなく競合。ローカルの新しい編集を守りつつ、サーバ版も失わないよう複製に退避する。複製はサーバへも送り、次回 push で消えないようにする |

## 4. 実行時の安全ルール（engine.ts）

1. **1 件の失敗で全体を止めない。** マップごとに try/catch し、失敗は `failed` に記録して次へ進む。
2. **オフライン・ネットワーク例外を外へ投げない。** `RemoteClient` は例外ではなく結果型で失敗を返す。
   同期が丸ごと失敗しても、ローカルのレコードは 1 バイトも書き換えない。
3. **`forkLocalCopy` は必ず「複製を保存 → サーバ版を取得 → 元 ID を上書き」の順。**
   逆順にすると、複製保存の直前に落ちたときにローカル版が消える。
4. **サーバ版の取得に失敗したら、元 ID は上書きしない。** 複製だけが増えるのは許容するが、
   失われるのは許容しない。
5. **`push` が 409 を返したら、返ってきた `serverMap` を使って判定をやり直す。**
   実質 #10 / #14 に落ちるので `forkLocalCopy` になる。ローカル版は必ず残る。
6. **`applyRemoteDelete` はローカルのノードを消さない。** `deletedAt` を立てるだけ。
7. **`StaleWriteError` で異常終了しない。** サーバ版の書き戻し（`pull` / `pullRestore`）が
   拒否されたら #18 に倒す。それ以外の書き込みが拒否された場合は `failed` に記録して
   元 ID を触らない（ローカルが新しいので、次回の同期で push 側に回る）。
8. **`deleteLocalHard` をどの経路でも呼ばない。** 物理削除は同期の責務ではない。

## 5. 却下した案

| 案                                              | 却下理由                                                                                        |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Last-Write-Wins（`updatedAt` が新しい方を採用） | クライアントの時計を信用することになり、新しいローカル編集を黙って消す経路ができる。§6 に反する |
| ノード単位のマージ                              | 親子関係の整合性を壊す組み合わせが作れてしまう。Phase 1 の複雑さに見合わない                    |
| CRDT（Yjs / Automerge）                         | §37 で明示的に禁止。Phase 1 はマルチデバイスの逐次利用であり、同時編集はスコープ外              |
| 競合時にユーザーへモーダルで即時確認            | 「考える流れを止めない」（§40-2）に反する。まず両方を安全に保存し、通知は非破壊的に出す         |

## 6. 未解決事項

- 複製されたマップ（`forkLocalCopy` の結果）を UI でどう見せるか。現状はタイトル末尾に接尾辞を付け、
  `SyncSummary.conflicts` で呼び出し側に返すだけ。通知 UI は担当 A / エディタ側の課題。
- 論理削除されたマップの物理削除タイミング（保持期間）。Phase 1 では墓標を残したままでよい。
- **#18 は収束しない可能性がある。** 担当 A の `saveMap` はローカルの方が新しいとサーバ版の
  書き戻しを常に拒否するため、元 ID はローカル版のまま固定される。毎回サーバ版の複製が
  増え続けることは無い（複製は push 後に synced になり、以降は一致するため）が、
  元 ID が `both-modified` のまま残り得る。根本的な解決には、担当 A 側に
  **サーバが決めた `version` をそのまま書ける経路**（`saveMapFromServer` 相当、
  ステイルチェックを迂回する書き込み）が必要。そこが入ったら #18 は通常の `pull` に戻せる。
