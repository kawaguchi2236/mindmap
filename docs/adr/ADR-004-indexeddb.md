# ADR-004: ローカル永続化レイヤ

## ステータス

採用（2026-09-13）／決定者: 担当 A（基盤・ローカル保存）

---

## 背景

エディタはローカルファースト（CLAUDE.md §5）で、クラウドが落ちていても編集と保存が続けられなければならない。判断基準は §32 ADR-004 の「信頼性・スキーマ移行・トランザクション・API の小ささ・TypeScript での扱いやすさ」。

## 決定

1. **ラッパーは `idb`（jakearchibald/idb）を使う。** 生の IndexedDB API を直接は使わない。
2. **保存の単位はマップ1件**（`MindMapDocument` = マップのメタ情報＋ノード全件）。ノードを1件1レコードにはしない。
3. **公開 API は `src/lib/db/types.ts` の `MapRepository` だけ**。画面・機能から `indexedDB.open()` を呼ばない。

### ストア構成

| ストア | key | 値 | index |
|---|---|---|---|
| `maps` | `map.id` | `MindMap`（メタ情報のみ） | `updatedAt` / `userId` / `deletedAt` |
| `nodes` | `map.id` | `{ mapId, nodes: MindMapNode[] }` | — |
| `syncMeta` | `mapId` | `SyncMeta` | — |

`maps` と `nodes` を分けるのは、一覧画面がノード本体を読まずに済ませるため。保存は**必ず両ストアを1トランザクション**で書き、片方だけ書かれた状態を作らない。

## 理由

- `idb` は Promise 化と型付けだけを足す薄いラッパーで、IndexedDB の意味論（トランザクション・バージョン移行）をそのまま残す。Dexie のようにクエリ言語やリアクティブ層まで持つものは、3ストアしかない今の規模には過剰（§19 §37）。
- マップ単位の保存にすると、**保存が1トランザクションで原子的に終わる**。「ノードだけ保存されて親子関係が壊れる」という、復旧しようのない壊れ方が構造的に起きない（§6「便利さのためにユーザーのデータを危険に晒さない」）。500〜1000 ノードなら丸ごと読み書きしても速度は問題にならない。
- リポジトリ 1 枚を挟むことで、クラウド同期（担当 B）もマップ一覧も同じ入口を使い、IndexedDB の詳細が画面側に漏れない。

## 影響

- スキーマを変えるときは `src/lib/model/types.ts` の `SCHEMA_VERSION` を上げ、**既存データを消さない増分マイグレーション**を書く（§6）。`upgrade` コールバックでストアを作り直さない。
- `saveMap` が `version` と `updatedAt` を進める。呼び出し側は触らない。
- `saveMap` は保存前に既存レコードを読み、**古い version で新しいデータを上書きしようとしたら `StaleWriteError` を投げる**。§6「新しいローカル版を古いサーバ版で上書きしない」をローカル側にも適用する。
- `deleteMap` は論理削除のみ（`deletedAt`）。物理削除の関数は用意しない。
- `claimGuestMaps(userId)` は `userId` を書き換えるだけで、マップを1件も消さず作り直さない（§14 ゲストマップの保全）。
- IndexedDB が使えない環境（プライベートウィンドウ等）では `IndexedDbUnavailableError` を投げ、**黙って失敗させない**（§29「ローカルデータが危険なので明示せよ」）。

## 却下した選択肢

- **Dexie.js**: 機能は十分だが、この規模ではクエリ層もリアクティブ層も使わない。バンドルと学習コストに見合わない。
- **localStorage**: 同期 API でメインスレッドを止め、容量も足りない。
- **ノード1件＝1レコード**: 部分更新は速いが、保存の原子性を自前で守る必要が生まれ、壊れ方が最悪になる。Phase 1 の規模では利点がない。
- **OPFS / File System Access API**: Phase 1 の要件（§3）に無く、ブラウザ対応も揃わない。
